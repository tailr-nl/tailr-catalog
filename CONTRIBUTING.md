# Contributing

Thanks for helping. Connectors, plugins and translations are all welcome.

1. **Fork** this repository and make your change in `connectors/`, `plugins/` or `translations/`.
2. **Keep the `"$schema"` line** at the top of `connector.json` or `plugin.json`, so your editor checks it.
3. **Check it:** `npx tailr check <folder or file>`. It must pass.
4. **Test it** in your own Tailr Core: add your fork as a source in *Settings → Sources* (*Add connector source*, or *Add plugin source*, which goes through the Danger zone with an authenticator app), install it from *Connections → Available* or *Plugins → Available* and try it.
5. **Bump the version** of what you changed, and the version in `connectors/index.json` for a connector.
6. **Open a pull request** with what it does, how you tested it, and which systems or versions it supports.

**Rules**
- **No secrets:** no tokens, passwords or customer data, also not in examples or tests.
- **Personal data is marked** in a connector with `privacy`, `sensitivity` and `audience`. Use the standard pattern (see below).

**Personal data: the standard pattern**

For a list without a search field that would return people (customers, orders with names, mandates):
1. **The list has no personal data.** Leave out names, email, phone, address and account numbers with `transform` (`select` or `exclude`). Keep what is not traceable to a person: id, number, status, amounts, dates, country.
2. **Looking up a person goes one at a time,** in a separate function with `privacy`: a required `lookup` (id, number or email), `sensitivity` per field, and a low `maxRecords`. The AI gets pseudonyms.
3. **An overview with names is only for Apps (API),** and only where it is useful (a dashboard, a tool): a separate function with `audience: "api"`. The AI does not see it.

Functions that write keep their level (`write` or `admin`). `tailr check` must pass without `personal_data_unmarked` warnings, with one exception: an overview only for Apps (API) (step 3) keeps the real field names (such as `voornaam`), and then still gets that warning. Do not rename fields to avoid it. The check cannot yet mark functions only for Apps (API) with `sensitivity` without the one-at-a-time rule; that is joepherrmann/tailr-core#216. Examples: `list_orders`, `list_customers` and `list_orders_with_names` in [woocommerce.json](connectors/woocommerce.json), and [Mollie](connectors/mollie/README.md#persoonsgegevens).
- **Plugins are trusted code** that runs without a sandbox: they are reviewed closely, and must only use the plugin API (`@tailr/plugin`).
- **Texts copied from someone else's documentation or API specification** must have a license that allows it. Mention the source in `NOTICE`.
- **By contributing**, you agree that your contribution is licensed under the Apache License 2.0.

## Overview content (`presentation`)

A connector, plugin or structured translation file may provide `presentation.intro`, up to six `presentation.examples` (`prompt` and a non-empty `requires` list), and `presentation.whatsNew`. Text is English or `{ "en": "…", "nl": "…" }`; it is plain text, never HTML. Use `adminOnly: true` for administration content. No examples are generated by the core when these fields are absent.

A connector uses local function names in `requires`; a plugin or translation uses fully qualified names such as `dashboards__list`. A prompt is shown only when the user can access every required function through AI. News is one item per newly available module, not one per function. Raise the module version when changing content. Translations require the structured format with `messages`; keep their version in `translations/index.json`.

See the matching JSON schema in `schemas/` and the core documentation `docs/presentation.md`. The installed core must support `presentation` to display it; older cores ignore the optional metadata.

## Variants (`variantOf`): generate, do not edit

Some connectors offer a second way to sign in to the same system, such as Google Analytics with your own Google account next to a service account. The variant must have exactly the same functions as the main connector. Do not edit it by hand: generate it with `scripts/make-variants.mjs`.

- **Change the main connector only**, for example `connectors/google-analytics/`. Then run `node scripts/make-variants.mjs google-analytics` (or without an id for all connectors).
- **What the script copies:** everything from the main connector, including `tools`, `scripts`, `presentation`, `limits` and the version, plus `context.md` and `tools/` for a folder connector.
- **What it replaces,** from a small configuration block per connector at the top of the script: `id`, `name`, `variantOf`, `variantTitle`, `description` (the main description plus a sentence), the sign-in settings in `vars`, `setup`, `hosts`, `auth`, and a few sentences in the texts of functions (such as "het serviceaccount"). A sentence that is no longer in the main connector stops the script, so a changed text is never silently left behind.
- **A folder connector gets a folder variant** (`connectors/<id>-signin/`), because a single JSON file cannot refer to `tools/*.ts`. The variant gets its own short `README.md` from the configuration.
- **The script updates `connectors/index.json`** with the path and version of the variant.
- **Check** that nothing is stale with `node scripts/make-variants.mjs --check`, and run `tailr check` on the main connector and on the variant.

To add a variant for another connector, add an entry to `VARIANTS` in the script.

## Language and presentation

Use English source text and provide Dutch in the same `{ "en": "…", "nl": "…" }` structure for connector descriptions and settings labels (`vars[].label` and `description`). Mark unfinished connectors with `maturity: "beta"`; keep test notes and fixed function counts out of their descriptions. This metadata needs a core that supports localized connector settings: release the matching core change before this catalog update.

Plugin screens use the host translation and date helpers and inherit the Tailr theme. Keep one page title and move destructive row actions into an action menu with confirmation. A user's own role, connection and dashboard names remain as entered.
